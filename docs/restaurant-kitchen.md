## 菜品工序后台

测试终端的「菜品工序后台」打开宽幅管理面板，横向卡片显示接单、各道工序、送餐与返程，八道菜竖向排列。手机每行左右滑动。每卡展示真实工位、基础加工秒数与对应美术；点击图片可播放循环 WebP，预览不提交业务操作。实时状态区分等待点击、走位、排队、加工与完成，只有真实工位加工显示蓝色圆环和倒计时。

后台、单菜测试和料理教材均通过 `kitchenRecipesInMenuOrder` 筛选 `KITCHEN_FLOWS`，与菜谱共用 `restaurantRecipeMenuOrder` 排序。菜谱同级资源按目录定义顺序显示，当前开局依次为蛋包饭、拿铁、三明治、柠檬气泡茶、草莓甜甜圈；后续补一道流程后自动进入后台，无需再维护一份显示清单。

`restaurant-kitchen-assets.js` 是场景和后台的统一资源注册表：v1 静态图、v2 旧两菜循环、v3 三明治/柠檬茶与 v4 松饼/布丁/抹茶/汉堡的透明道具与循环动画。成品继续引用 foods 中原有菜品，不重复生成成品。

新来客及高级顾客的后续点餐统一通过 `restaurant-arrive`/guest-order factory 生成手动 v4 订单。旧 `restaurant-start` 兼容接口不扩大 v1 自动排程范围，已保存的无 workflow 的已上线菜品订单仍按原计时有效，不迁移或重置存档。

## 玩家操作与结算

1. 客人入座后，点击菜品气泡只接单，不开始取料，也不生成后续工序的时间线。
2. 冰箱上出现食材圆圈；点击后，员工才移动到冰箱并开始取料。圆圈留在原工位，走路时显示“前往中”，到达工位后才启动倒计时；蓝色边缘只显示实际加工进度，食材图上叠加剩余秒数。
3. 当前工序完成后，员工停下，下一工位出现可点击圆圈。每一步都需要单独点击；等待、刷新、切换视角或打开终端均不会自动推进。
4. 装盘或打包完成后，还需要玩家点击送餐。员工实际端菜到顾客桌上后，顾客用餐 4.5 秒，才能点击收取小鱼干与成长。

工序间等待及装盘完成都不结算。钱包与成长仍通过共用服务端规则发放，前端动画不能产生奖励。

## 时间、员工和工位

默认一位员工。雇佣伙伴后，每位员工可以分别处理一单。新流程只在玩家点击时为当前操作生成服务端时间线，包含移动和加工；点击送餐才生成端菜与返程。员工从首次取料起绑定这一订单，包括工序之间等待玩家的时间，直到送餐返程完成后才能处理下一单。

每个工位同时只能有一位员工操作。若工位已被占用，点击会被拒绝，且不会扣除体力；玩家需要等工位空闲再点击。移动不占工位，不会为尚未点击的工序提前预约。

冰箱每级缩短取料时间 15%；料理台每级缩短其他加工步骤时间 15%。订单保存厨房等级快照，因此中途升级不会突然完成旧订单。步骤圆环显示当前实际加工进度，员工位置按同一时间线插值。工序道具只在对应员工实际加工时显示，完成后收起；冰箱箱体持续保留，只有取料时开门。

员工训练与同一调度器衔接：速度影响走路和取料，熟练度影响其他加工，体力与耐力决定能连续处理多少操作及何时需要恢复。首次取料时保存员工能力快照；训练升级只影响后续新订单。体力按本次点击扣除；新逐步订单仅在休息室恢复，旧协议按各自历史规则验证。体力账本保留已执行工作，已经结账移除的订单不会让员工提前恢复。返程必在用餐 4.5 秒内完成，领取并移除订单时不会删掉仍在途中的员工。

## 顾客与存档兼容

顾客模块为每桌保留 `party`。同桌两位顾客可以各点一份；厨房两份订单共用桌号，但分别接单、加工和送达。客人 6 秒入座之前不能接单，员工保持空闲，不会提前取料。同桌两单只有在合法 `party.members` 中属于同一桌时才允许共享送餐桌号。

旧订单没有 `workflow` 时保留原时间、收入和手动送餐规则；已有 v1 时间线继续兼容。正常顾客到店的蛋包饭和拿铁使用 v2 逐步点击流程。旧调试 `restaurant-start` 保留 v1 自动预演，不能用它代表正常营业的交互。旧餐厅没有 `levels.fridge` 时只补 1 级冰箱。其他菜品仍保留已有简化流程，后续可以逐道加入声明式步骤。

## 后续菜谱接入接口

规则与接口：

- `src/restaurant-kitchen-layout.js` 的 `INTERACTIVE_KITCHEN_ZONES`：十区边界、员工工作点与独立道具锚点。4/5 分界对齐原场景灶台接缝 48.6%；底部道具锚点约为场景高度的 87%，落在台面上。
- `src/restaurant-kitchen.js` 的 `KITCHEN_FLOWS`：菜谱步骤，字段为 `id/zoneId/label/durationMs/prop/carrying`；`kitchenInfo(restaurant, now)` 提供统一只读投影。原 `KITCHEN_ZONES` 继续用于 v1 存档验证，不作为新场景布局。
- `src/restaurant-kitchen-interactive.js` 的 `createInteractiveWorkflow`：创建未接单、没有预约时间段的 v2 订单。
- `acceptInteractiveWorkflow`：记录玩家接单，不绑定员工、不取料。
- `advanceInteractiveWorkflow`：验证并执行玩家刚点击的当前一步；`stepId: 'delivery'` 为单独的送餐操作。
- `validKitchenWorkflow`、`validKitchenReservations` 统一分派 v1/v2 验证。v2 通过重建每次点击的路线、耗时和体力扣除，拒绝跳步、提前完成及伪造时间线。

客户端动作仅为 `restaurant-kitchen-accept {orderId}` 与 `restaurant-kitchen-step {orderId, stepId}`。服务端使用自己的时钟，客户端不能指定员工、时间或奖励。

### 并行订单的场景操作圈（2026-10-19）

每份已接订单独立渲染下一步或正在执行工序的操作圈，选择另一份订单只改变查看目标，不再隐藏前一份的按钮。行走时保留圈，到达工位后各自显示蓝色圆环和数字倒计时；一份菜完成工序或送达时，只更新、移除属于它的圈。多单同时显示桌号，同工位或相邻工位的操作圈按 44px 点击区域错开，并避让「操作教程」按钮。同工位操作仍受原工位互斥与员工派工校验约束。

`kitchenActionPresentations` 由同一份只读厨房投影生成所有订单的按钮状态；场景按订单 ID 保留 DOM，只有该单步骤变化才替换食材图片。倒计时、可点击状态和工位占用逐圈更新，不更改工序、体力或保存协议。

完整回归 1357 项：1356 通过、1 项真实 PostgreSQL 环境跳过、0 失败；未运行会另开预览的 local-model-preview。共享构建 `assets/index-DuUw6x1Y.js` 通过全部 7 个存档入口一致性检查。共享 5174 网页实测两道菜交替推进：拿铁等待萃取时，蛋包饭取料/洗菜仍保留拿铁按钮；两位员工可同时打奶泡/打蛋，两圈各自显示 3 秒倒计时，每人完成 3 次操作后体力各为 70。共用冰箱的两个按钮相距 58px、标明桌号，没有页面横向溢出。证据在 `artifacts/restaurant-parallel-prompts/`。

新增菜谱应先定义工序和素材，再使用同一调度器。不要在前端自行增加经验、缩短保存时间或给两个员工同时占用同一工位。客户端只提交订单意图，不能传入员工编号、工位时间线或奖励金额。

渲染在 `src/restaurant-kitchen-ui.js` 和 `src/restaurant-kitchen.css`。员工与当前工序圆圈 DOM 保持挂载，位置按已点击工序的时间线推进。圆圈直径 44 CSS px，点击后留在原位，到达工作点才更新蓝色加工环与图上数字。正在执行的同一道工序不能重复点击；其他订单和菜单仍可操作。厨房名称与等级放在视角、教程按钮上方；正常营业不挂出旧的流程跟踪面板。减少动态效果系统设置会使用静态道具。

终端的“操作圈配色”提供奶油米黄、晴空浅蓝、薄荷奶绿、蜜桃奶橘、香芋淡紫五款。所有样例使用相同食材与蓝色进度，便于比较底色；点击后立即更新实际场景，只保存本地外观偏好，不产生云端经营操作。

## 出餐、返程和休息室动线

正常新到店的逐步制作订单使用 v4，保存创建时的 `layoutCapacity`，扩桌不会改写已有时间线；v2/v3 保存记录继续按旧协议验证。

`src/restaurant-kitchen-routing.js` 统一生成所有明确转弯点：出餐走左侧中轴 `x=47.5`，返程走右侧中轴 `x=54.5`，两者都通过厨房门洞 `y=65.5`，不能从桌边斜穿侧墙。各排桌下横通道为 `y=40/52/64`，先沿横道到桌边再向桌子靠近；回程先退回同一横道，再进入返程中轴。八桌布置才启用中央加桌的旁路。

去休息室沿第二排横通道向右，到门前再进门；送餐后耗尽体力时直接从该桌进入横通道去休息，不绕回厨房。休息结束再派工时，沿第二排横道回到返程中轴，经厨房门洞和内部走道前往工位。路径中的每段都为水平或垂直线，时间、体力与抵达判定均使用同一保存路线。

## 即时反馈与后台保存

餐厅使用共用云端队列，不另建存档或缓存前缀。已有订单的接单、逐步制作、送餐与收款先在本地投影中即时显示，再用原 `operationId` 静默保存。首次成功读取存档前仍不能操作，读取后即使断网也可继续排队；普通保存与工序衔接等待不会禁用其他餐厅操作或弹出保存提示。

本地视觉时间线和服务端实际时间线分别保存。即使本地工序比服务端早结束几百毫秒，玩家点击下一步也会被保留，后台等真实前序加工完成才提交，不传入客户端时间，不跳过服务端加工。到店产生的新订单编号与设施购买结果仍以服务端确认结果为准。

断网、超时、限流、5xx 或未知写入结果保留原操作与本地预览，并自动重试；联网事件与实时连接恢复会立即唤醒队列。只有明确的业务拒绝才撤销对应预览并提示。队列沿用原存档的待提交键，刷新后可恢复；测试入口仍按其约定刷新恢复默认。HTTP 与实时回执使用同一操作编号去重，不能重复扣费或结算。
