## 合并前的代码观察

以下是原交接阶段只读核对 `server/court.mjs`、`server/index.mjs`、`server/github-store.mjs`、`src/court.js` 时的观察。后续隔离测试结果以统一集成记录为准，生产验证尚未执行。

- 本次实现接入独立 PostgreSQL：一案完整 JSONB、事务行锁、数据库确认提交后才响应；数据库故障不回退临时文件。本机开发仍保留原子 JSON 文件存储。生产数据库尚未创建或配置。
- 当前线上仍为原存储版本；养猫的 GitHub 存储不能证明案件已有云端持久化。合并后的数据库、图片字节和迁移结果均需要重新核对。
- 新实现仅恢复过期的共享分析尝试，避免新实例打断旧实例的有效任务；本实例正常关闭时取消自己的分析并记录可重试中断。每项均待测。
- 当前前端会缩放截图并重新编码为 JPEG。验收必须区分用户选中的原文件、实际提交的图片字节和展示缩略图，不能将三者混称为“原图”。

以上为代码观察，不是功能验收结论。后续实现若有变化，以合并后的明确版本为准。

## 待测场景与验收标准

| 编号 | 待测场景 | 待执行步骤 | 验收标准 |
| --- | --- | --- | --- |
| P01 | 案件创建与确认保存 | 在允许测试后创建案件；等待存储写入完成，再读取案件。 | 返回成功时，案件已存在于明确的持久化目的地；案件 ID、标题和初审轮次一致。存储未配置或写入失败时明确报错，不显示“已保存”。 |
| P02 | 双方入席与等待 | A、B 分别认领角色；A 先提交证词和截图，B 暂不提交并短暂离线。 | 角色互斥；A 的提交已持久化且锁定；双方看到等待 B 的状态；不会提前调用 AI，也不要求双方始终同时在线。 |
| P03 | 双方提交与判词保存 | B 提交同一轮证词；模拟 AI 返回固定判词，随后重新读取。 | 双方均提交且保存成功后才启动一次分析；判词正文、模型标识、推理强度、生成时间及对应轮次均可恢复；失败时不能展示伪造判词。 |
| P04 | 截图字节完整性 | 比较提交基线、持久化内容、恢复后的图片字节及 SHA-256；打开历史截图查看文字。 | 实际提交图片的字节数及 SHA-256 在保存、读取、重启和迁移后完全一致。完整截图可以读取，不能只剩缩略图、失效临时链接或文件名。若宣称保留用户原文件，还必须独立验证原文件字节或可核对的原文件哈希；重新编码 JPEG 的哈希不能冒充原文件哈希。 |
| P05 | 角色权限与隐私 | 使用 A、B 原凭据、无凭据、伪造凭据及其他案件凭据分别读取、提交和重试。 | 只有本案有效角色可读取证词、截图和判词或提交自己的陈词；无凭据读取不包含私密内容；跨案件凭据无效；不能代替另一方提交。持久化记录仅保存角色凭据的必要安全形式，公开响应及日志不泄露凭据。 |
| P06 | 角色持久化 | 保存角色后重启服务，再用原浏览器会话继续读取和提交；第三会话尝试重新认领已占用角色。 | 原角色凭据仍有效；席位不会因服务重启而变空，也不会被第三会话抢占。浏览器会话丢失与服务器丢档需明确区分，不能通过昵称绕过权限。 |
| P07 | 复议历史 | 完成初审后，双方补充不同证词和截图，完成至少两轮复议；回看每轮并检查模拟 AI 输入。 | 新内容进入新轮次；原证词、截图、判词和时间保留且不可被覆盖。复议输入包含此前双方证词、证据、判词及本轮补充；旧判词被标为此前分析，不当作新增事实。每轮仍等待双方提交。 |
| P08 | 页面刷新与增量同步 | A 编辑补充陈词时 B 先发起复议；刷新 A；在判词更新与在线状态更新交错时继续轮询。 | 未提交的文字草稿不会被轮次切换或旧响应覆盖；已提交记录完整恢复；仅在线状态的响应不推进客户端完整历史版本，避免漏掉新提交或判词。未提交截图若未实现刷新恢复，应明确提示重新添加，不能误称已服务端保存。 |
| P09 | 服务重启 | 在等待另一方、已完成初审及已完成复议三种状态下重启服务，使用原案件链接读取。 | 案件、角色、所有已提交证词、截图和判词均保留；版本与轮次不倒退；恢复内容和哈希与基线一致；已完成轮次不会重新调用 AI。 |
| P10 | 重新部署与无本机缓存恢复 | 按约定在测试环境重新部署或启动全新实例，不复用旧进程内存或临时磁盘；读取原案件。 | 从目标持久化存储恢复完整案件，不能只依赖旧实例、本机缓存或临时磁盘。若存储暂不可用，明确失败，不能悄悄创建空案件或宣称原数据已恢复。 |
| P11 | 写入失败与版本可见性 | 模拟拒绝写入、权限不足、存储超时或磁盘错误；分别在创建、认领、提交、复议和判词保存时发生；恢复存储后重试。 | 写入未确认成功前不发布新版本或“保存成功”。明确回滚的认领不占席位，明确回滚的提交不锁定证词、不触发 AI；旧案件与版本保持可用。COMMIT 已成功但回应丢失属于结果未知，必须先重新读取核对，不能宣称必未保存。当前认领回应丢失可能无法取回新凭据，应单独记录，不能把它当回滚成功。 |
| P12 | 保存延迟与读取交错 | 在候选判词进入保存阶段时阻塞存储确认，同时发起授权 GET、公开 GET 和在线状态读取；释放保存后再比对存储。 | 保存完成前，任何响应都不能宣告未持久化的新判词或版本。完成后响应版本与持久化记录一致；无半份截图、部分证词或混合轮次。应使用可控制的保存阻塞与释放信号验证，不以增加固定等待时间掩盖竞态。 |
| P13 | 旧案件迁移 | 备份旧格式的等待、已判、复议及中断案件；执行明确的迁移流程；比对源和目标，再重复迁移。 | 案件 ID、角色凭据哈希、轮次 ID、证词、截图字节、判词、时间与版本不丢失；迁移可重复执行而不复制轮次、不重新分析。确认目标保存并完整核对前不删除或覆盖源数据；目标已有冲突或源数据损坏时明确停止并保留可恢复资料。 |
| P14 | 并发与冲突处理 | 同时认领同一角色、同时提交双方陈词、同时发起复议及重试；若支持多个实例，再通过两个实例写入同一案件。 | 同一角色只有一个有效认领；双方陈词都保留；同一复议只产生一个新轮次；存储冲突不会以旧版本覆盖新证词或判词。若实现仅支持单实例，配置与说明必须明确限制，不能宣称多实例安全。 |
| P15 | AI 中断恢复 | 在调用前、调用中、收到结果后但保存前，以及保存后但响应前分别模拟中断或重启。 | 证词与证据始终可恢复；中断轮次有明确状态和重试入口，不永久停在“正在分析”。已持久化判词恢复后直接展示。保存失败不能发布成功判词；恢复过程不自动盲目重发状态未知的外部调用。 |
| P16 | 防止重复 AI 调用 | 记录模拟 AI 的请求 ID、轮次和次数；连续点击提交/重试、模拟响应丢失并刷新，再访问已完成轮次。 | 同一轮正常双提交只调用一次；并发重试最多接受一个新分析尝试；已完成并持久化的轮次不再调用。状态未知后的显式重试需可追踪并说明可能重复分析，不能把本地去重宣称为外部计费的严格一次保证。 |
| P17 | 大小与格式限制 | 按合并后公布的边界准备超限、伪装格式、损坏图片和超轮次材料。 | 明确拒绝不支持或超限输入；失败不改变案件版本、既有截图和证词；客户端提示与服务端限制一致，不能在保存中途截断证据。 |
| P18 | 数据库备份恢复 | 将已完成初审和复议的快照恢复到隔离数据库，启动新服务核对全部内容；不覆盖生产数据库。 | 双方凭据、所有轮次、证词、实际上传截图哈希和判词完整恢复；备份权限受限且日志不含隐私，不能仅以备份文件存在作为恢复通过。 |

真实 PostgreSQL 的双实例测试位于 `tests/court-postgres.test.mjs`，只在设置专用 `COURT_TEST_DATABASE_URL` 时启用，默认跳过。不得把生产连接地址用作测试地址；此项使用模拟 AI，不需要真实 OpenAI 调用。实际执行需等统一测试通知。

## 判词展示与修复任务优化：追加待测项

下列条目对应本轮截图参考的界面优化；P01–P18 继续保留。正式判词、蓝色根因卡、蓝粉双方责任评述及黄色判令，均须来自本案已保存的真实分析。修复进度只描述双方对任务完成情况的确认，不代表感情、道德、责任或安全评分。以下项目尚未执行，也不授权提前运行测试、提交案件、调用真实 AI、预览服务或部署。

| P19 | 正式判词与结构化来源 | 使用明确标识的模拟结构化判词，核对正式判词卡、根因蓝卡、蓝粉双方责任卡、黄色判令与保存内容。 | 各卡片展示对应本案、对应轮次的已保存字段，并保留模型、生成时间和分析轮次来源；不得从参考图或固定模板填入本案事实、责任结论或进度。双方配色表示席位，不暗示性别或谁更可信。根因属于有依据的分析，不能被包装成已确认事实或心理诊断。 |
| P20 | 证据依据、信心与责任不足 | 分别提供证据充分、双方主张冲突、截图缺上下文及无足够证据的模拟结果；核对卡片与证据引用。 | 明确区分可见证据、当事人主张、推断和未知信息；引用能定位到实际轮次、陈词或截图，不出现不存在的证据。信心只描述结论的不确定性，不能冒充证明真实性的数值。证据不足时明确“无法判断谁的责任更大”，不默认各半、不虚构责任百分比、不为了完整布局补造结论。 |
| P21 | 旧文本判词历史兼容 | 读取和迁移仅含原有文本判词的初审、复议案件，与新版结构化轮次混合展示。 | 旧判词全文、模型和时间原样保留并可阅读；缺少结构化字段时使用明确的文本展示，不补造根因、责任比例或修复任务。读取旧历史不重新调用 AI；兼容处理不改写既有证词、截图、版本或确认记录。 |
| P22 | 每项任务双确认与真实进度 | 对含固定 N 项修复任务的计划，依次执行无人确认、仅 A 确认、A/B 均确认、全部双确认及一方撤回。 | 每项任务有稳定标识；只有 A、B 对同一项都确认时，该项计为完成。进度依据服务端已保存的确认状态，按“双确认完成项数 ÷ 当前计划任务数”计算；仅一方确认不加完成项，撤回任一确认在保存成功后减少相应完成项。无任务时不显示虚假的 100%。确认表示当事人报告的完成情况，不能宣称 AI 已验证实际行为。 |
| P23 | 自身角色权限与旧轮只读 | 以 A、B、无凭据及跨案件凭据操作任务；篡改请求中的角色、任务、计划与轮次；尝试改动旧轮。 | 服务端从有效凭据确定角色，不能通过请求字段替对方确认或撤回；不能改其他案件的任务。仅允许当前可操作计划的自身确认，未知任务和失效计划明确拒绝；旧轮任务与确认记录只读。客户端禁用按钮不能替代服务端权限检查。 |
| P24 | 复议生成新计划、保留旧确认 | 双方在初审计划中完成部分任务并撤回一项确认，再发起复议，生成文字相同或不同的新任务；回看旧轮。 | 新复议关联新的计划或轮次标识，不沿用旧计划的完成状态；即使任务文字相同，也不自动把旧确认当作新任务完成。旧任务、各方有效确认及撤回后的状态完整保留，可核对来源但不可继续修改。新分析不得把“用户确认任务完成”当作新截图或已独立核实的事实。 |
| P25 | 确认保存失败与未知结果 | 在确认和撤回时模拟明确回滚、存储超时、回应丢失及失败后的重试；比较界面、版本和持久化记录。 | 保存尚未确认时明确显示等待状态，不乐观展示已完成勾选、提升进度或减少任务。明确回滚保持上一确认状态和进度；回应丢失先刷新或重读核对，不声称必未保存，也不盲目重发可能过时的意图。失败不能丢失旧计划或确认状态，也不能触发 AI。 |
| P26 | 两实例并发确认与稳态请求幂等 | A、B 经两个实例同时确认同一任务；在状态未改变时重复同一确认请求；交错确认、撤回与旧响应到达；记录模拟 AI 调用次数。 | 两方确认都保留，不能相互覆盖；对相同当前布尔状态的重复赋值不增加版本、不重复保存或调用 AI。按保存后的版本同步状态，晚到的旧响应不能覆盖客户端已知的新版本。确认与撤回之间迟到的旧请求属于新的状态赋值，当前不承诺操作 ID 去重或严格一次；未知结果应先重读核对，界面不能声称此类重放已被去重。任务确认端点的 AI 调用次数始终为零。 |
| P27 | 任务记录的重启、迁移与备份恢复 | 对含任务、双确认、单确认及已撤回状态的案件执行约定的重启、新实例恢复、旧数据迁移及隔离备份恢复。 | 计划及任务标识、所属轮次、任务正文、来源、各方有效确认状态与时间完整保存；撤回后该方确认为未确认，恢复后进度仍可从当前记录重新计算。迁移不清空旧轮确认、不自动补确认、不重新调用 AI；旧格式无任务时保持无任务。当前不将完整确认事件日志、撤回时间或操作 ID 当作已实现字段。 |
